8부. 대용량 데이터 처리 — 청크·SQL·Parquet

정정(통합 검토 중 발견): 이 절을 처음 작성할 때 "원문(Chapter 08)"이라는 표현을 사용했으나, 이는 사실이 아니다. 원본 PDF(machine_learning_with_python.pdf, 총 427쪽)를 직접 재확인한 결과, 원문은 Chapter 01~07로 구성되어 있으며 Chapter 07(군집화)이 427쪽에서 그대로 끝난다 — Chapter 08은 존재하지 않는다. 이 절은 원문에 대응하는 장이 전혀 없는, 이 교재가 새로 추가한 절이다("금융 빅데이터 분석"이라는 교재 제목에 맞게 대용량 데이터 처리 기법을 다뤄야 한다는 1단계 설계 판단에 따라 추가됨). 이전 버전에서 "원문(Chapter 08)은 ~을 다룬다"고 서술한 것은 존재하지 않는 원문 내용을 사실처럼 기술한 오류이며, 이 정정으로 대체한다. 이 절이 다루는 청크 단위 읽기·SQL 연동·Parquet 변환 기법은 원문의 어떤 부분을 재구성한 것이 아니라 전부 새로 설계한 내용이며, 사례로는 2~4·6·7부에서 이미 사용한 UCI 신용카드 실제 데이터(30,000행)를 그대로 50배 복제해 150만 행 규모의 "거래 로그"를 만들어 실습 대상으로 삼았다. 중요한 주의: 이 복제는 값 자체를 변형하지 않고 행만 반복한 것이므로, 이 절에서 나오는 평균·비율 등의 수치는 새로운 통계적 사실이 아니라 원본 30,000행의 값과 정확히 같다 — 이 절의 목적은 "숫자가 무엇을 말하는가"가 아니라 "이만큼 큰 데이터를 어떻게 효율적으로 다루는가"라는 기법 자체다.

1. 금융 상황과 해결할 질문

지금까지(2~7부)는 3만 행 정도의 데이터를 다뤘고, pd.read_csv()로 통째로 불러와도 컴퓨터가 무리 없이 처리했다. 하지만 실제 카드사의 거래 로그는 하루에도 수백만~수천만 건씩 쌓인다. 이런 데이터를 노트북 한 대의 메모리에 통째로 올리려 하면 메모리가 부족해 프로그램이 멈추거나(MemoryError), 심하게 느려질 수 있다.

메모리에 한 번에 다 올릴 수 없을 만큼 큰 데이터에서, 어떻게 같은 통계량(평균, 그룹별 비율 등)을 정확하게 계산할 수 있는가? 그리고 이런 데이터를 저장할 때 파일 형식(CSV vs Parquet)이 처리 속도와 저장 공간에 어떤 차이를 만드는가?

2. 학습목표와 선수지식

  1. 데이터를 청크(chunk, 조각) 단위로 나누어 읽으면서, 전체를 한 번에 읽은 것과 정확히 같은 집계 결과를 만드는 방법을 설명할 수 있다.
  2. SQL(구조화 질의 언어)을 이용해 데이터베이스에서 필요한 집계만 계산해오는 방식과, 이것이 왜 메모리 효율적인지 설명할 수 있다.
  3. 행 지향(CSV) 저장 방식과 열 지향(Parquet) 저장 방식의 차이를 이해하고, 각각이 유리한 상황을 구분할 수 있다.

선수지식: 2부의 pandas 기본 조작, 파이썬 표준 라이브러리에 포함된 sqlite3에 대한 사전 지식은 필요 없다(이 절에서 처음부터 설명).

3. 직관적 설명

두꺼운 전화번호부에서 "김"씨 성을 가진 사람이 몇 명인지 세야 한다고 생각해보자. 책 전체를 통째로 외워서(메모리에 올려서) 세는 대신, 한 페이지씩 넘기며(청크 단위로) "김"씨 수를 세어 나가다가 마지막에 다 더하면 같은 답이 나온다 — 책 전체를 손에 들고 있을 필요가 없다. SQL 데이터베이스는 한 걸음 더 나아가, "몇 명인지 세어서 알려줘"라고 요청만 하면 도서관 사서(데이터베이스 엔진)가 알아서 책을 넘겨가며 세어 답만 돌려준다. 그리고 전화번호부를 "이름, 전화번호, 주소"를 한 사람씩 통째로 인쇄하는 대신 "모든 사람의 이름을 먼저 다 인쇄하고, 그다음 모든 전화번호를 인쇄하는" 방식(열 지향)으로 재구성해두면, "이름만 필요한" 작업을 할 때 전화번호·주소 부분은 아예 펼쳐볼 필요가 없어 훨씬 빠르다.

4. 용어와 수식

청크(chunk): 큰 파일을 한 번에 읽지 않고 정해진 행 수(예: 100,000행)만큼씩 나누어 읽는 단위.

증분 평균(가중 결합 평균): 두 그룹(또는 청크)의 평균을 각각 알고 있을 때, 전체를 다시 계산하지 않고 두 평균을 표본 크기로 가중 결합해 전체 평균을 구할 수 있다.

$$\bar{x}_{\text{전체}} = \frac{n_A \bar{x}_A + n_B \bar{x}_B}{n_A + n_B}$$

이 공식을 청크마다 반복 적용하면(또는 합계와 개수만 누적하면), 전체 데이터를 한 번에 메모리에 올리지 않고도 정확히 같은 평균을 계산할 수 있다.

SQL(Structured Query Language): 데이터베이스에 "어떤 데이터를 어떻게 계산해서 달라"고 요청하는 언어. SELECT AVG(컬럼) FROM 테이블 GROUP BY 그룹컬럼처럼, 계산 자체를 데이터베이스 엔진에 맡기고 결과만 돌려받는다.

행 지향 저장(row-oriented, 예: CSV) vs 열 지향 저장(column-oriented, 예: Parquet): CSV는 한 행(레코드) 전체를 순서대로 이어붙여 저장한다 — 한 행을 읽으려면 그 행의 모든 컬럼을 다 읽어야 한다. Parquet은 반대로 같은 컬럼의 값들을 모아서 저장한다 — 특정 컬럼 몇 개만 필요할 때 나머지 컬럼은 아예 디스크에서 읽지 않아도 된다(컬럼 가지치기, column pruning). 또한 같은 컬럼의 값은 서로 비슷한 경우가 많아(예: EDUCATION은 1~4 사이 정수만 반복) 압축 효율도 높다.

5. 손으로 확인하는 작은 숫자 예제

청크1 = $[10, 20, 30]$(평균 20, 개수 3), 청크2 = $[40, 50]$(평균 45, 개수 2)이 있다고 하자.

가중 결합 평균:

$$\bar{x} = \frac{20 \times 3 + 45 \times 2}{3+2} = \frac{60+90}{5} = \frac{150}{5} = 30$$

전체 데이터 $[10,20,30,40,50]$을 한 번에 평균 내도 $150/5=30$으로 정확히 같은 값이 나온다(코드로 확인, 7.2절). 이 원리를 그대로 확장하면, 청크가 수백 개여도 "각 청크의 합계와 개수"만 누적해서 더하면 전체를 한 번에 메모리에 올리지 않고도 정확한 전체 평균을 구할 수 있다.

6. 데이터 정의와 분석 설계

데이터 성격에 대한 명확한 안내: 이 절의 large_transactions.csv(150만 행)는 2~4·6·7부에서 쓴 UCI 신용카드 실제 데이터(30,000행)를 record_id만 새로 부여하고 값은 그대로 50번 복제한 것이다. 즉 150만 행 안에는 서로 다른 3만 개의 실제 레코드가 각각 50번씩 반복해서 들어있다. 이렇게 만든 이유는, 이 절에서 다루는 청크 처리·SQL·Parquet 같은 인프라 기법은 데이터의 통계적 성질과 무관하게 "얼마나 큰 데이터를 어떻게 저장·처리하는가"의 문제이기 때문이다 — 자유롭게 재현 가능한 실제 대용량 금융 거래 로그를 구하지 못해, 실제 데이터를 복제해 규모만 키우는 방식을 택했다. 이 절에서 계산하는 평균·비율은 원본 30,000행의 값과 정확히 같으며, "150만 명의 새로운 고객 통계"로 해석해서는 안 된다.

검증 규칙: 이 절은 예측 모델을 만들지 않으므로 학습/테스트 분할은 필요 없다. 대신 "청크 처리 결과가 전체를 한 번에 읽은 결과와 정확히 일치하는가"를 매 단계 직접 비교해 검증한다 — 이는 3부 이후 지켜온 "주장을 실제 실행으로 검증한다"는 원칙을 대용량 처리 맥락에 적용한 것이다.

7. 단계별 실습 코드와 설명

실행 환경: 2~7부와 동일(Python 3.11+/pandas 3.0.2/numpy 2.4.4/matplotlib 3.10.9) + pyarrow(Parquet), psutil(메모리 측정), 표준 라이브러리 sqlite3. 전체 실행 시간 약 67초(대용량 CSV 생성 포함, 최초 1회만 발생).

7.1 대용량 CSV 생성 (실제 데이터 복제 — 값 변형 없음)

import pandas as pd
import os

raw = pd.read_csv("UCI_Credit_Card.csv")
df = raw.drop(columns=["ID"]).rename(
    columns={"PAY_0": "PAY_1", "default.payment.next.month": "default"}
)
df["EDUCATION"] = df["EDUCATION"].replace({0: 4, 5: 4, 6: 4})
df["MARRIAGE"] = df["MARRIAGE"].replace({0: 3})

N_COPIES = 50  # 30,000 x 50 = 1,500,000행
LARGE_CSV = "large_transactions.csv"
with open(LARGE_CSV, "w", encoding="utf-8") as f:
    header_written = False
    for copy_i in range(N_COPIES):
        chunk = df.copy()
        chunk.insert(0, "record_id", range(copy_i * len(df), (copy_i + 1) * len(df)))
        chunk.to_csv(f, header=not header_written, index=False)
        header_written = True

csv_size_mb = os.path.getsize(LARGE_CSV) / (1024 ** 2)
print(f"행 수={N_COPIES * len(df):,}, 파일 크기={csv_size_mb:.1f}MB")

실제 실행 결과: 150만 행, 파일 크기 176.2MB의 CSV가 생성된다.

7.2 전체 로드 vs 청크 처리 — 같은 통계량, 다른 메모리 사용량

import psutil, time

process = psutil.Process(os.getpid())

# 방식 1: 전체를 한 번에 로드
mem_before = process.memory_info().rss / (1024**2)
t0 = time.time()
full_df = pd.read_csv(LARGE_CSV)
full_mean_bill1 = full_df["BILL_AMT1"].mean()
full_default_rate_by_edu = full_df.groupby("EDUCATION")["default"].mean().round(4)
t_full = time.time() - t0
mem_after_full = process.memory_info().rss / (1024**2)
del full_df

# 방식 2: 청크 단위로 읽어 증분 계산
CHUNK_SIZE = 100_000
t0 = time.time()
total_sum, total_count = 0.0, 0
edu_sum = {}
peak_mem = mem_before
for chunk in pd.read_csv(LARGE_CSV, chunksize=CHUNK_SIZE):
    total_sum += chunk["BILL_AMT1"].sum()
    total_count += len(chunk)
    for edu, group in chunk.groupby("EDUCATION"):
        s, c = edu_sum.get(edu, [0.0, 0])
        edu_sum[edu] = [s + group["default"].sum(), c + len(group)]
    peak_mem = max(peak_mem, process.memory_info().rss / (1024**2))
t_chunk = time.time() - t0

chunk_mean_bill1 = total_sum / total_count
chunk_default_rate_by_edu = pd.Series(
    {edu: s / c for edu, (s, c) in edu_sum.items()}
).sort_index().round(4)

print(f"전체 로드: 시간={t_full:.2f}초, 메모리 증가량={mem_after_full - mem_before:.1f}MB")
print(f"청크 처리: 시간={t_chunk:.2f}초, 최대 메모리 증가량={peak_mem - mem_before:.1f}MB")
print("full_mean_bill1:", round(full_mean_bill1, 4), "chunk_mean_bill1:", round(chunk_mean_bill1, 4))
print("full_default_rate_by_edu:\n", full_default_rate_by_edu)
print("chunk_default_rate_by_edu:\n", chunk_default_rate_by_edu)

실제 실행 결과: 두 방식 모두 BILL_AMT1 평균이 51223.3309로 정확히 일치하고, EDUCATION별 연체율도 (1: 0.1923, 2: 0.2373, 3: 0.2516, 4: 0.0705)로 완전히 같다. 하지만 메모리 사용량은 전체 로드 방식이 295.9MB 증가한 반면, 청크 처리 방식은 최대 60.7MB만 증가했다 — 약 1/5 수준이다(그림 8-1). 실행시간도 청크 처리가 3.40초로 전체 로드(9.43초)보다 오히려 더 빨랐는데, 이는 전체 로드 방식이 150만 행 전체를 담는 큰 DataFrame을 한 번에 만드는 오버헤드가 있는 반면 청크 처리는 작은 조각을 순차적으로 가볍게 처리하기 때문이다.

7.3 SQLite에 적재 후 SQL로 동일한 집계

import sqlite3

t0 = time.time()
conn = sqlite3.connect("large_transactions.db")
for chunk in pd.read_csv(LARGE_CSV, chunksize=CHUNK_SIZE):
    chunk.to_sql("transactions", conn, if_exists="append", index=False)
conn.execute("CREATE INDEX idx_education ON transactions(EDUCATION)")
t_sql_load = time.time() - t0

t0 = time.time()
sql_mean_bill1 = pd.read_sql(
    "SELECT AVG(BILL_AMT1) AS avg_bill1 FROM transactions", conn
)["avg_bill1"].iloc[0]
sql_default_rate_by_edu = pd.read_sql(
    "SELECT EDUCATION, AVG([default]) AS default_rate, COUNT(*) AS n "
    "FROM transactions GROUP BY EDUCATION ORDER BY EDUCATION", conn
)
t_sql_query = time.time() - t0
sql_db_size_mb = os.path.getsize("large_transactions.db") / (1024**2)
conn.close()

print(f"[SQLite 적재] 적재 시간={t_sql_load:.2f}초, DB 파일 크기={sql_db_size_mb:.1f}MB")
print(f"[SQL 쿼리] 실행시간={t_sql_query:.3f}초, BILL_AMT1 평균={sql_mean_bill1:.4f}")
print(sql_default_rate_by_edu)

실제 실행 결과: SQLite 적재에 12.21초가 걸렸지만(파일 크기 109.2MB), 일단 적재된 후에는 AVG·GROUP BY 쿼리가 0.804초 만에 완료되고 결과(BILL_AMT1 평균 51223.3309, EDUCATION별 연체율 0.1923/0.2373/0.2516/0.0705)도 앞선 두 방식과 정확히 일치한다. SQL 쿼리 방식의 장점은, 파이썬 코드로 반복문을 짜지 않아도 데이터베이스 엔진이 알아서 청크 단위 계산과 유사한 최적화를 내부적으로 수행해준다는 점이다 — 특히 이번처럼 반복 조회가 필요한 상황(대시보드, API 등)에서는 한 번 적재해두고 여러 번 빠르게 쿼리할 수 있어 유리하다.

7.4 Parquet 변환 및 CSV 대비 성능 비교

import pyarrow as pa
import pyarrow.parquet as pq

writer = None
for chunk in pd.read_csv(LARGE_CSV, chunksize=CHUNK_SIZE):
    table = pa.Table.from_pandas(chunk, preserve_index=False)
    if writer is None:
        writer = pq.ParquetWriter("large_transactions.parquet", table.schema, compression="snappy")
    writer.write_table(table)
writer.close()

parquet_size_mb = os.path.getsize("large_transactions.parquet") / (1024**2)

# 전체 컬럼 읽기 비교
t_csv_full = time.time(); _ = pd.read_csv(LARGE_CSV); t_csv_full = time.time() - t_csv_full
t_pq_full = time.time(); _ = pd.read_parquet("large_transactions.parquet"); t_pq_full = time.time() - t_pq_full

# 컬럼 2개만 읽기 비교 (컬럼 지향 저장의 장점)
t_csv_2col = time.time(); _ = pd.read_csv(LARGE_CSV, usecols=["BILL_AMT1", "default"]); t_csv_2col = time.time() - t_csv_2col
t_pq_2col = time.time(); _ = pd.read_parquet("large_transactions.parquet", columns=["BILL_AMT1", "default"]); t_pq_2col = time.time() - t_pq_2col

print(f"CSV 크기={csv_size_mb:.1f}MB vs Parquet 크기={parquet_size_mb:.1f}MB (압축비 {csv_size_mb/parquet_size_mb:.2f}배)")
print(f"전체 컬럼: CSV {t_csv_full:.2f}초 vs Parquet {t_pq_full:.2f}초")
print(f"2개 컬럼만: CSV {t_csv_2col:.2f}초 vs Parquet {t_pq_2col:.2f}초")

실제 실행 결과:

전체 컬럼을 다 읽을 때도 Parquet이 약 2.6배 빠르지만, 필요한 컬럼 2개만 읽을 때 차이가 극적으로 벌어진다(1.24초 → 0.04초, 약 31배) — 이것이 열 지향 저장의 "컬럼 가지치기" 효과를 가장 잘 보여주는 결과다(그림 8-1).

8. 결과 읽는 법과 업무상 의미

청크 처리는 "정확성을 희생하지 않고" 메모리를 절약한다: 7.2절에서 확인했듯 청크 처리 결과와 전체 로드 결과는 소수점까지 완전히 같다. 이는 청크 처리가 "근사치를 빠르게 구하는 방법"이 아니라 "정확한 값을 메모리 효율적으로 구하는 방법"이라는 점을 강조한다. 합계와 개수처럼 "누적 가능한" 통계량(평균, 합계, 개수, 최댓값/최솟값)은 청크 처리가 항상 가능하지만, 중앙값이나 분위수처럼 전체 데이터의 순서를 알아야 하는 통계량은 청크만으로는 정확히 계산하기 어렵다는 한계도 있다(10절에서 다시 설명).

SQL과 Parquet은 "한 번 준비하고 여러 번 활용"할 때 유리하다: SQLite 적재(12.21초)나 Parquet 변환(4.65초)은 그 자체로 시간이 걸리는 작업이다. 하지만 일단 준비해두면 이후 쿼리·읽기는 훨씬 빠르다 — 데이터를 한 번만 훑고 끝낼 것이라면 청크 처리로 충분하지만, 같은 데이터를 반복해서 여러 각도로 분석해야 하는 상황(대시보드, 매일 갱신되는 보고서)이라면 SQL 데이터베이스나 Parquet으로 미리 변환해두는 투자가 이후 시간을 크게 절약해준다.

복제 데이터라는 한계를 다시 강조: 이 절의 모든 수치(평균 51223.33 등)는 새로운 사실이 아니라 2부에서 이미 다룬 30,000행의 값 그대로다. 실무에서 실제로 150만 건의 서로 다른 거래가 있다면 평균·분산 같은 통계량 자체는 이 절의 값과 다르게 나올 것이다 — 이 절은 오직 "그 정도 규모를 어떻게 다루는가"라는 기법만을 검증한다.

10. 흔한 오해와 오류

  • 오해 1: "청크 처리는 전체 로드보다 항상 느리다(대신 메모리만 아낀다)." 이번 실험에서는 오히려 청크 처리가 더 빨랐다(3.40초 vs 9.43초). 항상 그런 것은 아니지만("느려도 메모리를 아낀다"는 통념과 달리), 큰 DataFrame을 한 번에 만드는 오버헤드가 클 때는 청크 처리가 속도 면에서도 유리할 수 있다.
  • 오해 2: "청크 처리로는 어떤 통계량이든 정확히 계산할 수 있다." 평균·합계·개수·최댓값처럼 "부분 결과를 나중에 합칠 수 있는" 통계량은 청크 처리가 정확하지만, 중앙값이나 특정 분위수는 전체 데이터를 정렬해야 정확히 구할 수 있어 단순 청크 누적으로는 안 된다(근사 알고리즘이 별도로 필요하다) — 연습문제 6에서 이 차이를 직접 확인한다.
  • 오류 1: "SQL 결과와 pandas 결과가 다르면 SQL이 틀렸을 것이다." 이 절에서는 세 가지 방식(전체 로드, 청크 처리, SQL)의 결과를 모두 직접 비교해 정확히 일치함을 확인했다. 실무에서 결과가 다르다면 SQL 자체보다 데이터 타입 변환(예: 문자열로 저장된 숫자), NULL 처리 방식의 차이를 먼저 의심해야 한다.
  • 오류 2: "Parquet은 항상 CSV보다 좋으니 무조건 Parquet만 쓰면 된다." Parquet은 컬럼 일부만 읽거나 반복적으로 읽는 상황에 유리하지만, 사람이 텍스트 편집기로 직접 열어보거나 다른 시스템과 간단히 데이터를 주고받아야 하는 상황에서는 사람이 읽을 수 있는 CSV가 여전히 실용적이다. 파일 형식은 "항상 우월한 것"이 아니라 사용 목적에 따라 고르는 것이다.

11. 핵심 요약

메모리에 다 올릴 수 없는 대용량 데이터는 청크 단위로 나눠 읽으면서 합계·개수 같은 누적 가능한 통계량을 증분 계산하면, 전체를 한 번에 읽은 것과 정확히 같은 결과를 훨씬 적은 메모리로 얻을 수 있다. SQL 데이터베이스는 이런 계산을 데이터베이스 엔진에 위임해 반복 조회를 빠르게 만들고, Parquet 같은 열 지향 저장 형식은 필요한 컬럼만 골라 읽을 때 CSV보다 훨씬 빠르다(이번 실험에서는 2개 컬럼만 읽을 때 약 31배). 이 절의 모든 실험은 UCI 실제 데이터를 복제해 규모만 키운 것이므로, 수치 자체가 아니라 처리 기법의 정확성과 효율성에 주목해야 한다.

12. 연습문제

개념 문제
1. 평균은 청크 단위로 정확히 누적 계산할 수 있는데, 중앙값은 왜 그렇게 할 수 없는지 설명하라.
2. Parquet이 CSV보다 "컬럼 몇 개만 읽을 때" 특히 빠른 이유를 열 지향 저장 방식의 구조로 설명하라.

계산 문제
3. 청크1의 평균이 100(개수 40), 청크2의 평균이 150(개수 60)일 때, 전체 평균을 가중 결합 공식으로 계산하라.
4. 어떤 컬럼의 합계가 청크1에서 500(개수 10), 청크2에서 300(개수 5), 청크3에서 700(개수 15)로 나왔을 때, 전체 평균을 계산하라.

실습 문제
5. N_COPIES를 50에서 200으로 늘려 600만 행 규모로 만든 뒤, 전체 로드 방식이 여전히 정상적으로 동작하는지, 메모리 증가량이 어떻게 달라지는지 확인하라.
6. BILL_AMT1의 중앙값을 (a) 전체 로드 후 median()으로 구한 값과 (b) 각 청크의 중앙값을 단순 평균한 값을 비교해, 둘이 다르다는 것과 그 이유를 확인하라.

연습문제 해설(별도)

  1. 평균은 "합계"와 "개수"라는 두 숫자만 알면 다른 부분의 값을 몰라도 정확히 계산할 수 있다(가중 결합 공식). 하지만 중앙값은 "정확히 가운데 순서에 있는 값"을 찾아야 하므로, 전체 데이터를 정렬하거나 각 값의 상대적 순서를 알아야 한다 — 청크 단위로 나눠서는 그 순서 정보가 청크 경계를 넘어 유지되지 않는다.
  2. 열 지향 저장은 같은 컬럼의 값들을 디스크에 연속으로 모아 저장한다. 특정 컬럼만 필요하면 그 컬럼이 저장된 부분만 디스크에서 읽으면 되고, 나머지 컬럼이 저장된 부분은 아예 건드릴 필요가 없다. 반면 CSV(행 지향)는 한 행 안에 모든 컬럼이 섞여 있어서, 컬럼 하나만 필요해도 모든 행을 끝까지 읽어야 한다.
  3. $\bar{x} = (100 \times 40 + 150 \times 60)/(40+60) = (4000+9000)/100 = 130$.
  4. 전체 합계 $=500+300+700=1500$, 전체 개수 $=10+5+15=30$. 평균 $=1500/30=50$.
  5. (실습형) 메모리 증가량은 대략 행 수에 비례해 커질 것으로 예상되며(600만 행이면 약 4배), 청크 처리 방식은 청크 크기가 고정되어 있으므로 메모리 사용량이 거의 그대로 유지될 것이다 — 이 차이가 데이터가 커질수록 더 뚜렷해지는 것을 확인하는 것이 목적이다.
  6. (실습형) 각 청크의 중앙값을 단순 평균한 값은 전체 데이터를 정렬해 구한 진짜 중앙값과 일반적으로 다르다 — 청크마다 값의 분포가 조금씩 다르면 "청크별 중앙값의 평균"이 전체 중앙값을 대표하지 못하기 때문이다(이 절이 사용하는 복제 데이터는 각 청크가 원본과 거의 같은 분포를 가지므로 차이가 작을 수 있으나, 실제 비복제 데이터에서는 차이가 더 클 수 있다).
